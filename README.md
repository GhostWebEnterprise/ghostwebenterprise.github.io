## About

This repository contains the source for the **GhostWeb Enterprise project hub** hosted with GitHub Pages. The site provides a central entry point for GhostWeb projects, their current development status, repositories and project-specific information.

GhostWeb Enterprise focuses on privacy-oriented software across secure communication, network privacy, AI-assisted development and Android platform security.

## Projects

| Project | Focus | Development status |
| --- | --- | --- |
| **GhostWeb Signal** | Privacy-focused secure Android messaging based on established Signal/Molly components with GhostWeb UI and security enhancements | 🟠 Active development |
| **GhostWeb VPN** | Network privacy tooling and VPN clients with emphasis on verified endpoints, leak protection and fail-closed behavior | 🟠 Active development · not release-ready |
| **GhostWeb AI** | AI-assisted software development, agent workflows, planning, coding, testing and delivery | 🟠 Active development · not release-ready |
| **GhostOS** | Privacy-focused Android ROM with security hardening, Privacy Center, Auditor, verified boot and OTA goals | 🟠 Active development |

## Project principles

GhostWeb projects are developed around a common set of goals:

- **Privacy by design** — minimize unnecessary exposure of user data.
- **Secure defaults** — security-sensitive functionality should fail safely where practical.
- **Open development** — project code, changes and development status should be inspectable where repositories are public.
- **Verifiable releases** — signing, checksums and automated verification should be used where supported by each project.
- **Clear status communication** — experimental and unfinished functionality should be identified as such.
- **Upstream respect** — projects derived from open-source software should retain appropriate attribution and licensing.

## Security

Security vulnerabilities should **not** be disclosed through public issues when doing so would expose users or an unpatched weakness.

For GhostWeb Signal, follow its dedicated security policy and private vulnerability-reporting process. Other project-specific security policies should be used where available.

Never publish credentials, API tokens, signing keys, keystores, private user data or exploit details for an unresolved vulnerability in a public issue.

## Contributing

Contributions should be scoped to the relevant project whenever possible. For changes to this website, keep project descriptions accurate, preserve responsive behavior and clearly distinguish experimental work from stable functionality.

Before submitting changes:

1. verify links and project names;
2. test affected pages on desktop and mobile layouts;
3. avoid claims that a development project is production-ready;
4. keep security-sensitive information out of commits and issues.
